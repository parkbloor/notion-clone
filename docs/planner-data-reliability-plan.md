# 일간 플래너 데이터 복구·저장 안정화 개발서

> 작성일: 2026-08-23
> 상태: P0~P5 구현 및 격리 자동 검증 완료 · P6부터 신규 일정 사용 흐름과 기존 기능의 SQLite 통합 진행
> 원칙: 기능 추가보다 기존 일정 보호를 먼저 완료하고, 원본을 자동 이동·변환·삭제하지 않는다.

## 1. 확인된 현재 상태

- 실제 볼트 읽기 전용 감사에서 플래너 원본 16개와 일정 발생 217개를 확인했다.
- 일정 ID와 날짜 기준 고유 일정은 189개이며 다른 원본과 겹치는 발생은 28개다.
- 주요 기존 일정은 14개 Day Planner 블록과 18개 날짜에 분산되어 있다.
- 현재 일간 플래너로 설정된 볼트들의 일정 홈 메모에는 Day Planner 블록이 없다.
- 따라서 실제 삭제뿐 아니라 `일정 홈만 읽는 새 화면`과 `과거 분산 원본`의 단절이 일정이 사라진 것처럼 보이는 주요 원인이다.

## 2. 목표 구조

```text
지정한 일정 볼트
└─ _planner/
   ├─ planner.sqlite3
   ├─ backups/
   └─ exports/
```

- 일정과 루틴의 단일 원본은 페이지 블록이 아닌 트랜잭션 저장소가 담당한다.
- Day Planner 블록과 패널은 같은 저장소를 보여 주는 뷰가 된다.
- JSON 내보내기와 자동 백업으로 이동성과 사람이 확인할 수 있는 복구 경로를 유지한다.

## 3. 단계

### P0. 기존 원본 감사와 백업 — 구현 완료

- 모든 초기화된 볼트의 `content.nct`를 읽기 전용으로 검사한다.
- 현재 `eventsByDate`, 구버전 `date/events`, 혼합·빈·손상 형식을 구분한다.
- 일정 홈 존재 여부와 홈 안의 Day Planner 블록 수를 별도로 표시한다.
- 날짜+일정 ID 기준 고유 수와 중복 발생 수를 계산한다.
- 명시적 버튼을 눌렀을 때만 모든 페이지 JSON과 플래너 메타파일을 ZIP에 복사한다.
- ZIP 내부 파일별 SHA-256 매니페스트를 만들고 다시 읽어 검증한 뒤에만 완료한다.
- 검사와 백업 모두 원본을 이동·변환·삭제하지 않는다.

### P1. 추가 유실 차단 — 구현 완료

- 저장 실패를 무시하는 fire-and-forget 경로를 제거한다.
- 일정 추가·수정·완료 후 서버 확인 결과를 UI에 표시한다.
- 구버전 또는 손상 데이터를 빈 값으로 간주한 채 덮어쓰지 못하게 한다.
- 90일 이전 원본은 아카이브 저장 성공을 확인한 뒤에만 페이지에서 제거한다.
- 실패한 변경은 미저장 상태와 재시도 경로를 유지한다.

구현 결과:

- 현재·구버전·혼합 플래너 JSON을 공통 파서로 읽으며 구버전 일정도 첫 수정에서 보존한다.
- 파싱 실패나 잘못된 필드 구조는 편집을 잠그고 복구 센터 백업을 안내한다.
- 일정 블록과 우측 빠른 패널 모두 즉시 저장 결과를 확인한다.
- 실패하면 무기한 오류 상태와 `다시 시도` 동작을 제공하고 성공 시 오류를 해제한다.
- 90일 이전 일정을 성공 확인 없이 아카이브로 보내고 원본에서 제거하던 자동 분리 동작을 중단했다.

### P2. 전용 일정 저장소 — 구현 완료

- Python 표준 `sqlite3`로 일정과 일일 회고를 트랜잭션 저장한다. 기존 루틴은 화면 전환 전까지 검증된 볼트별 파일 저장을 유지한다.
- 개발 서버 재시작, HMR, 페이지 구조 변경과 일정 원본을 분리한다.
- 이벤트 단위 생성·수정·완료·삭제 API와 낙관적 버전을 제공한다.
- 삭제는 즉시 제거하지 않고 복구 가능한 상태로 기록한다.

구현 결과:

- 앱 전체에서 하나의 `일정 데이터 볼트`를 지정하며 설정은 `vaults_root/.planner_data_config.json`에 저장한다.
- 선택한 볼트의 `_planner/planner.sqlite3`에 일정과 날짜별 회고 테이블을 생성하고 WAL 트랜잭션을 사용한다.
- 일정은 이벤트 단위 생성·범위 조회·수정·소프트 삭제·복원 API를 제공한다.
- 일정과 회고 수정은 `revision`을 비교하여 오래된 요청을 HTTP 409로 거부한다.
- P2에서는 기존 Day Planner 페이지를 읽거나 복사하거나 수정하지 않으며, UI도 아직 기존 원본을 계속 사용한다.

### P3. 기존 데이터 마이그레이션 — 구현 완료

- P0 감사 결과를 바탕으로 이동 대상 볼트와 원본을 사용자가 선택한다.
- 중복 후보와 충돌을 미리 보여 준다.
- 검증된 백업이 존재할 때만 복사를 허용한다.
- 마이그레이션은 반복 실행해도 결과가 늘어나지 않는 idempotent 방식으로 구현한다.
- 기존 Day Planner 블록은 삭제하지 않고 읽기 호환으로 남긴다.

구현 결과:

- 원본 볼트를 선택해 현재·구버전·혼합 Day Planner와 아카이브의 일정 및 일일 회고를 미리 집계한다.
- 현재 원본 파일 목록과 SHA-256이 정확히 일치하는 검증 ZIP이 없으면 복사 버튼을 활성화하지 않는다.
- 날짜와 일정 ID가 같은 중복은 하나로 합치며, 내용이 다른 충돌 수와 우선 선택한 원본 경로를 먼저 표시한다.
- 미리보기 지문과 백업 파일이 실행 시점에도 같아야 하나의 SQLite 트랜잭션으로 복사한다.
- 마이그레이션 원본 키를 별도 기록하여 반복 실행해도 중복 생성하지 않고, 기존 페이지와 아카이브는 수정하거나 삭제하지 않는다.
- 복사가 성공하면 저장소에 활성 상태를 기록하고 우측 오늘 일정 패널의 조회·추가·완료 처리를 SQLite로 전환한다.
- 기존 Day Planner 블록은 원본 일정 수를 표시하는 읽기 전용 보존 안내로 바꾸며, 저장소 상태 확인 실패 시에는 레거시 쓰기로 후퇴하지 않고 편집을 잠근다.

### P4. 일간 플래너 사용 흐름 간소화 — 구현 완료

- 첫 화면은 오늘 일정, 타임라인, 완료, 루틴 적용에 집중한다.
- AI·날씨·통계·가져오기·내보내기·아카이브는 보조 메뉴로 이동한다.
- 저장 중·저장 완료·오프라인 대기·저장 실패 상태를 항상 확인할 수 있게 한다.

구현 결과:

- 계획 허브의 첫 행동을 `오늘 일정` 하나로 줄이고 SQLite 활성 시 오늘 완료 수를 함께 표시한다.
- 주간 타임라인과 루틴 관리는 두 번째 영역에 유지한다.
- 일간 노트, 캘린더, 기록 통계, HTML 내보내기, 주·월·분기·연간 회고는 기본 접힌 `보조 도구`로 이동한다.
- SQLite 활성 시 보조 기간 통계도 레거시 블록이 아닌 전용 저장소의 기간 일정으로 계산한다.

### P5. 장애 회귀 검증 — 격리 자동 검증 완료

- 일정 생성 직후 새로고침
- 빠른 연속 수정과 드래그·리사이즈
- 백엔드 재시작 중 입력과 재연결
- Next.js HMR과 앱 종료·재실행
- 볼트 전환과 일정 홈 변경
- 두 창의 동시 수정과 충돌 복구
- 구버전·혼합·손상 원본 감사와 반복 마이그레이션

검증 결과:

- 임시 볼트와 실제 FastAPI 라우터를 사용해 일정 생성 후 클라이언트 재접속에서도 데이터가 유지되는지 확인했다.
- 두 편집자가 같은 revision에서 수정한 상황을 재현해 먼저 저장된 변경만 남고 오래된 요청은 HTTP 409로 거부되는지 확인했다.
- 소프트 삭제 후 일반 조회에서 숨겨지고, 최신 revision으로 복원하면 같은 일정 ID와 내용이 다시 나타나는지 확인했다. 오래된 revision의 복원도 HTTP 409로 거부된다.
- 구버전·혼합 원본 병합, 손상 원본 쓰기 잠금, 현재 원본과 백업 해시 불일치 차단, 반복 마이그레이션 무중복을 자동 테스트로 확인했다.
- 전체 백엔드 테스트 64건, 프런트 단위 테스트 24건, TypeScript, 변경 범위 ESLint와 Next.js 16.3.2 프로덕션 빌드를 통과했다.
- 이 검증은 실제 사용자 볼트와 실행 중인 개발 서버를 변경하지 않았다. 실제 원본의 백업·마이그레이션과 실행 중 앱의 백엔드 중단·재연결, HMR, 두 창 조작 검증은 설정 화면에서 사용자가 실행할 때 최종 확인한다.

## 5. 다음 개발 로드맵

### P6. 기존 데이터 없이 새 일정으로 시작 — 다음 착수 단계

목표:

- 사용자가 기존 일정 백업·마이그레이션 없이 빈 SQLite 저장소를 명시적으로 활성화한다.
- 기존 페이지와 Day Planner 블록은 읽거나 수정하거나 삭제하지 않는다.

백엔드 계약:

- `POST /api/planner/store/activate-empty`를 추가한다.
- 요청 본문은 `{ "confirmation": "START_EMPTY" }`만 허용한다.
- 일정 데이터 볼트가 지정되지 않았거나 존재하지 않으면 HTTP 409를 반환한다.
- `events`는 삭제 항목 포함 0건, `reviews`는 0건이어야 한다. 하나라도 있으면 HTTP 409로 차단하고 초기화나 삭제를 대신 수행하지 않는다.
- 조건을 통과하면 하나의 트랜잭션에서 `meta.migration_complete=1`, `meta.activation_mode=fresh`를 기록한다.
- 이미 `activation_mode=fresh`로 활성화된 빈 저장소에 같은 요청을 반복하면 성공 결과를 반환한다.
- 마이그레이션 성공 시에는 `activation_mode=migration`을 기록해 두 경로를 상태에서 구분한다.
- 상태 응답에 `activationMode`, `canStartFresh`를 추가한다.

프런트엔드 계약:

- `PlannerDataVaultPanel`에 `새 일정으로 시작` 영역을 추가한다.
- 저장소가 비어 있고 아직 활성화되지 않았을 때만 버튼을 활성화한다.

### P7. 기본 일정 CRUD 완성

- 일정 행을 선택하면 제목·날짜·시작·종료·색상을 수정하는 편집 폼을 연다.
- 종료 시간이 시작 시간보다 빠른 입력을 클라이언트와 서버 양쪽에서 거부한다.
- 삭제 직후 실행 취소 토스트를 제공하고, 별도 삭제함에서 기간 내 삭제 일정을 복원한다.
- 수정·삭제·복원 모두 `expectedRevision`을 보내며 409 발생 시 최신 일정 다시 불러오기와 사용자 변경 재적용 중 선택하게 한다.
- 저장 중·완료·실패·재시도 상태를 일정 단위로 표시한다.
- 완료 기준은 생성·수정·완료·삭제·복원을 새로고침 후에도 확인하고 두 창 충돌에서 먼저 저장된 내용을 잃지 않는 것이다.

### P8. SQLite 하루 타임라인

- 기존 `PlannerTimeline`과 `usePlannerEventDrag`의 좌표 계산·미리보기 동작을 재사용하되 저장 대상만 SQLite API로 교체한다.
- 빈 슬롯 클릭 추가, 드래그 이동, 리사이즈, 5·10·15·30분 스냅, 현재 시각선, 완료 숨기기를 연결한다.
- 드래그 중에는 로컬 미리보기만 표시하고 마우스를 놓을 때 한 번만 revision 업데이트한다.
- 충돌이나 저장 실패 시 마지막 서버 위치로 되돌리고 재시도 경로를 보여 준다.

### P9. SQLite 루틴

- `routines` 테이블과 revision, 요일, 활성 상태, 자동 적용 정책을 추가한다.
- 기존 `_planner_routines.json`은 검증 백업 후 명시적으로 복사하며 자동 삭제하지 않는다.
- 루틴 생성·수정·삭제, 오늘 적용, 날짜 이동 시 자동 적용, 특정 날짜 제외를 연결한다.
- 같은 `routineId+date`의 자동 생성 일정이 중복되지 않게 데이터베이스 제약 또는 트랜잭션 검사를 둔다.

### P10. 일정 상세 기록과 타이머

- 현재 저장 가능한 `scheduled`, `clockIn`, `clockOut`, `elapsed`, `log`, `subtasks`, `energy`를 새 상세 패널에 연결한다.
- 하위 작업은 안정적인 ID를 유지하고 빠른 연속 입력을 직렬화한다.
- 타이머는 앱 재시작 후 서버 시각을 기준으로 경과 시간을 복구하며 한 일정만 실행 가능하게 한다.
- 알림 권한 실패는 일정 저장 실패로 취급하지 않는다.

### P11. 일일 회고

- 날짜별 회고를 조회·편집하고 revision 충돌, 저장 상태, 재시도를 제공한다.
- 회고 화면에 해당 날짜의 계획 수·완료 수·예정 시간·실행 시간을 표시한다.
- 주·월·분기·연간 회고는 같은 SQLite 회고와 일정 범위 조회를 사용한다.

### P12. 주간 타임라인과 월간 캘린더

- 주간 화면은 한 번의 범위 조회로 7일 일정을 표시한다.
- 요일 간 드래그는 날짜와 시간을 하나의 revision 업데이트로 저장한다.
- 월간 캘린더에 일정 개수와 완료 상태를 표시하고 날짜 선택 시 같은 일정 패널을 연다.
- 메모·기록 캘린더는 유지하고 일정 레이어를 시각적으로 구분한다.

### P13. 루틴 매트릭스와 장기 통계

- `WeeklyPlannerBlock`, `RoutineMatrixBlock`, `QuarterlyPlannerBlock`, `YearlyPlannerBlock`이 페이지 블록을 스캔하지 않고 공통 SQLite 조회 어댑터를 사용하게 한다.
- 루틴 달성률, 계획/완료 시간, 활동일, 월·분기·연간 추세를 같은 집계 규칙으로 계산한다.
- 레거시 원본 통계와 SQLite 통계를 한 화면에서 합쳐 표시하지 않는다.

### P14. 백업·가져오기·내보내기·아카이브

- 일정·회고·루틴을 포함한 버전형 JSON 백업과 검증 복원을 제공한다.
- 오늘·이번 주 HTML 내보내기가 SQLite 일정과 기존 기록 헤더를 함께 출력하게 한다.
- CSV 기간 내보내기와 삭제 일정/과거 일정 탐색 화면을 추가한다.
- 가져오기 미리보기에서 추가·중복·충돌 수를 보여 주고 하나의 트랜잭션으로 반영한다.

### P15. AI와 날씨

- AI는 현재 일정 snapshot과 revision을 기준으로 제안만 만들고, 추가·수정·삭제 diff를 사용자가 확인한 뒤 적용한다.
- AI 적용 중 일부만 저장되지 않도록 하나의 배치 트랜잭션 또는 전체 실패 계약을 사용한다.
- 날씨는 독립 설정과 기존 API를 유지하고 선택 날짜의 보조 정보로만 표시한다.

### P16. 전환 완료와 레거시 정리

- 시작·재접속·HMR·오프라인·두 창·볼트 전환·대량 일정 회귀를 실제 앱에서 검증한다.
- 모든 소비자가 SQLite를 사용하는지 `eventsByDate` 직접 읽기/쓰기 검색으로 확인한다.
- 기존 Day Planner 블록은 사용자가 명시적으로 삭제하기 전까지 읽기 전용으로 남긴다.
- 레거시 코드 제거는 별도 승인과 검증 백업 이후에만 수행한다.

- 실제 사용자 볼트를 사용하는 테스트, 자동 마이그레이션, 볼트 파일 삭제는 금지한다. 임시 볼트와 격리된 HTTP 앱을 사용한다.
- `vault_config.json`, `.planner_data_config.json`, 실제 `_planner/planner.sqlite3`를 테스트 산출물로 만들거나 커밋하지 않는다.

## 8. P0 안전 계약

- 실제 볼트 감사는 GET과 파일 읽기만 사용한다.
- 복구 ZIP은 `vaults_root/_planner_recovery_backups/`에 새 파일로 생성한다.
- 동일 파일을 덮어쓰지 않는다.
- 임시 ZIP은 전체 CRC와 파일별 SHA-256 검증을 통과해야 최종 이름으로 바뀐다.
- 실제 사용자 원본 백업 생성은 설정 → 볼트 기능 → 일정 복구 센터에서 사용자가 직접 실행한다.
