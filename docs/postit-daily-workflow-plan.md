# 포스트잇 기반 일간 워크플로우 개발 계획서

> 작성일: 2026-08-22
> 상태: 단일 하루 기록 블록·월간 기록 흐름·기록 허브·줄 복사/잘라내기 구현 완료 · 며칠간 실제 사용 관찰 중
> 대상: 일간 플래너 볼트, 일정 홈, Periodic Notes, 일간 템플릿, 블록 이동·복사
> 관련 문서: `planner-workflow-reorganization-plan.md`

---

## 1. 목적

낮에는 종이 포스트잇에 생각을 한 줄씩 기록하고, 밤에는 전용 일간 플래너 볼트에서 포스트잇을 정리한다.

이 기능의 성공 기준은 정보를 많이 저장하는 것이 아니다.

```text
낮: 판단 없이 수집
밤: 필요한 것만 처리
결과: 책상 위 미처리 포스트잇 0장
```

앱은 다음 네 가지 판단을 빠르게 수행하도록 돕는다.

```text
해야 할 일 / 장기 메모 / 아이디어 / 오늘 기록만 남김
```

---

## 2. 확정할 핵심 역할

### 2.1 일정 홈 메모

- 기존 Day Planner 일정과 루틴을 저장하는 유일한 메모다.
- 우측 Day Planner 패널의 조회와 빠른 추가 대상이다.
- 날짜별 일정은 기존 `eventsByDate` 구조를 유지한다.
- 포스트잇 원문을 모두 쌓는 장소로 사용하지 않는다.
- 장기적으로는 오늘 일간 노트와 세 장기 페이지로 이동하는 대시보드 역할도 맡는다.

### 2.2 일간 노트

- 종이 포스트잇을 밤에 옮겨 적고 처리하는 날짜별 작업대다.
- 포스트잇 한 장은 편집기 블록 하나로 입력한다.
- 일정 데이터의 저장소로 사용하지 않는다.
- 새 포스트잇 템플릿에는 `dayplanner` 블록을 넣지 않는다.
- 사용자가 `오늘 일간 노트 열기`를 실행한 경우에만 생성한다.

### 2.3 장기 페이지

- `해야 할 일`: 앞으로 실행할 항목의 현재 상태
- `장기 메모`: 다시 참고할 가치가 있는 정보
- `아이디어`: 창작·개발 등에 활용할 후보

세 페이지는 사용자가 직접 만들고 현재 메모를 목적지로 지정한다. 앱은 자동 생성하지 않는다.

### 2.4 주간·월간 노트

- 일간 노트를 다시 복사하는 장소가 아니다.
- 반복된 문제, 중요한 변화, 다음에 실행할 내용만 압축한다.
- 초기 구현에서는 자동 생성·자동 요약하지 않는다.

## 3. 목표 정보 구조

```text
일간 플래너 볼트
├─ 일정 홈
│  ├─ Day Planner
│  ├─ 오늘 일간 노트 열기
│  ├─ 해야 할 일 열기
│  ├─ 장기 메모 열기
│  └─ 아이디어 열기
│
├─ 일간 노트 YYYY-MM-DD
│  ├─ 미처리 포스트잇
│  ├─ 오늘 기록으로만 남길 내용
│  └─ 처리 결과
│
├─ 주간 노트 YYYY-WNN
├─ 월간 노트 YYYY-MM
├─ 해야 할 일
├─ 장기 메모
└─ 아이디어
```

일반 볼트에서는 위 진입점과 자동 동작이 모두 비활성화된다.

## 4. 현재 구현과의 충돌 목록

### C1. 일정 저장 위치 중복

현재 우측 Day Planner는 일정 홈만 읽고 쓰지만, `makeDailyTemplate()`이 만든 일간 노트에도 별도 `dayplanner` 블록이 들어간다.

이 상태에서는 홈 일정과 일간 노트 일정이 분리되며, 우측 패널에서 일부 일정이 보이지 않는 것처럼 느낄 수 있다.

### C2. 일간 노트 생성 경로 불일치

다음 경로가 서로 다른 일간 템플릿을 사용한다.

- 계획 허브의 `오늘 일간 노트`
- `Ctrl+Alt+D`
- 월간 캘린더 날짜 선택
- 사용자 지정 주기 노트 템플릿

일간 노트의 제목, 블록 구성과 플래너 포함 여부가 진입점에 따라 달라질 수 있다.

### C3. 구형 Day Planner 초기 콘텐츠

현재 일부 일간 템플릿은 다음 구형 구조를 만든다.

```json
{ "date": "...", "events": [], "routines": [], "autoApply": true }
```

현재 Day Planner의 기준 구조는 다음과 같다.

```json
{ "eventsByDate": {}, "reviewByDate": {} }
```

새로 생성하는 모든 플래너 콘텐츠는 현재 구조만 사용해야 한다.

### C4. 주기 노트 템플릿 범위

일부 주기 노트 템플릿 선택과 내장 템플릿 수정값은 전역 설정에 남아 있다. 복수의 일간 플래너 볼트를 사용할 경우 한 볼트의 템플릿 선택이 다른 볼트에 맞지 않을 수 있다.

### C5. 블록 복사 후 상태 분리

일간 노트의 할 일을 `해야 할 일` 페이지에 단순 복사하면 완료 상태가 서로 연동되지 않는다.

초기 단계에서는 이 문제를 수동 운영으로 관찰하고, 빠른 분류를 구현할 때 원본 기록과 실제 작업 상태의 역할을 명확히 분리한다.

## 5. 변경하지 않을 안전 계약

- 기존 Day Planner 블록과 일정 데이터를 삭제하거나 자동 이동하지 않는다.
- 기존 일간·주간·월간·분기·연간 노트를 변환하지 않는다.
- 기존 루틴과 `_planner_routines.json`을 유지한다.
- 기존 일정 아카이브와 기간 HTML 내보내기를 유지한다.
- 일반 볼트에 플래너 폴더·메모·설정 파일을 자동 생성하지 않는다.
- `vault_config.json`을 기능 설정 파일로 사용하거나 초기화하지 않는다.
- 페이지 제목이 아니라 페이지 ID로 홈과 목적지를 연결한다.
- 연결된 페이지를 찾지 못해도 다른 페이지를 대신 사용하지 않는다.

### P0 조사 결과 — 2026-08-22

#### 생성 경로

- 실제 새 일간 노트 생성 경로는 위 세 곳이다.
- 계획 허브만 설정의 사용자 지정 템플릿과 내장 템플릿 수정값을 반영한다.
- 단축키와 월간 캘린더는 사용자 템플릿 설정을 무시하고 서로 다른 하드코딩 템플릿을 적용한다.
- 세 경로 모두 기존 제목을 찾으면 페이지를 열기만 하며 기존 블록에는 템플릿을 다시 적용하지 않는다.
- 일간 노트 카테고리는 자동 생성하지 않는다. 기존 카테고리를 찾지 못하면 루트에 페이지를 만든다.
- 월간 캘린더는 한국어에서 `일간 노트`, 영어에서 `Daily Note`를 제목 접두사로 사용한다. 언어를 바꾸면 같은 날짜가 다른 제목으로 생성될 수 있다.

#### 데이터 형식과 집계 경계

- 계획 허브의 기본 일간 템플릿과 월간 캘린더는 `date/events/routines/autoApply` 구형 콘텐츠로 Day Planner를 초기화한다.
- 현재 Day Planner 편집기는 구형 콘텐츠를 일정으로 읽지 않고 빈 `eventsByDate`로 취급한다.
- 우측 Day Planner 패널은 지정된 일정 홈 한 페이지만 조회하고 빠른 추가도 그 페이지에만 저장한다.
- `WeekPlannerBlock`, `WeeklyPlannerBlock`, `RoutineMatrixBlock`, 분기·연간 플래너는 모든 페이지의 Day Planner 블록을 조회한다.
- 기간 HTML 내보내기도 모든 페이지를 읽으며, 같은 날짜와 같은 이벤트 ID 조합만 중복 제거한다. 제목과 시간이 같아도 이벤트 ID가 다르면 별도 일정으로 집계한다.
- 따라서 기존 일간 노트와 일정 홈에 같은 일정이 서로 다른 ID로 있으면 일부 요약과 내보내기에는 둘 다 나타날 수 있다.

#### 중복 생성과 저장 경계

- 프론트엔드 검사는 호출 시점에 로드된 `pages` 배열에서 완전히 같은 제목만 찾는다.
- 백엔드는 같은 제목의 페이지 생성을 금지하지 않으며 요청마다 새 UUID와 폴더를 만든다.
- 생성 중 잠금이나 날짜별 고유 키가 없어 빠른 연속 호출은 같은 날짜의 페이지를 둘 만들 수 있다.
- `addPage()`가 완료된 뒤 아이콘과 블록을 별도로 저장하므로 공통 생성 함수에서는 생성 중 상태와 후속 저장 실패를 함께 다뤄야 한다.

#### P1·P2에 반영할 결정

1. 신규 일간 노트에는 Day Planner를 넣지 않고 일정 홈만 새 일정의 저장소로 사용한다.
2. 세 진입점을 하나의 날짜 기반 생성 함수로 통합한다.
3. 저장 제목은 기존 한국어 형식 `일간 노트 YYYY-MM-DD`를 우선 유지하고, 탐색 시 기존 영어 제목도 호환 대상으로 검토한다.
4. 사용자 지정 템플릿이 Day Planner를 포함한 경우의 처리 규칙은 P2에서 명시적으로 정한다. 사용자 데이터이므로 조용히 삭제하지 않는다.
5. 기존 일간 노트와 그 안의 Day Planner는 수정하거나 자동 이전하지 않는다.
6. 검증은 스토어/API 모킹과 임시 테스트 볼트를 사용한다. 실제 사용자 볼트에는 조사·테스트용 페이지를 만들지 않는다.

## P1. 일정 저장 위치 단일화

### 목표

일정 홈을 새 일정의 유일한 저장소로 고정한다.

### 작업

1. 설정 문구를 `플래너 홈 메모`에서 `일정 홈 메모`로 명확히 변경
2. 우측 Day Planner가 일정 홈만 읽고 쓰는 현재 계약 유지
3. 일정 홈이 없으면 빠른 추가를 비활성화하고 설정 경로 안내
4. 일정 홈에 Day Planner가 없을 때는 사용자의 첫 빠른 추가 동작에서만 생성
5. 기존 일간 노트의 Day Planner 블록은 그대로 렌더링하고 편집 가능하게 유지
6. 신규 포스트잇 일간 템플릿에는 Day Planner를 넣지 않음

### 마이그레이션 원칙

- 기존 일간 노트의 일정은 자동으로 홈에 합치지 않는다.
- 같은 날짜의 일정 ID가 중복될 수 있으므로 자동 병합을 금지한다.
- 필요성이 확인되면 별도 `기존 일정 가져오기` 도구를 설계한다.

### 완료 조건

- [x] 기존 일정과 블록 수가 바뀌지 않는다.
- [x] 일정 홈 페이지 이름을 바꿔도 연결이 유지된다.

## P2. 일간 노트 생성 경로 통합

### 목표

어디에서 오늘 일간 노트를 열어도 같은 페이지와 같은 템플릿 결과를 얻는다.

### 작업

1. 날짜별 제목·기존 페이지 탐색·생성·아이콘·템플릿 적용을 공통 함수로 분리
2. 계획 허브, 단축키, 월간 캘린더가 공통 함수를 사용하도록 변경
3. 동일 날짜에서 반복 호출하면 기존 페이지를 열고 새 페이지를 만들지 않음
4. 저장 성공 전에는 템플릿 적용 완료로 표시하지 않음
5. 생성 실패 시 낙관적 페이지를 남기지 않고 사용자에게 오류 표시
6. 일간 노트 카테고리가 없으면 루트에 만들되 카테고리를 자동 생성하지 않음

### 현재 구조 호환

- 기존 `일간 노트 YYYY-MM-DD` 제목 형식을 우선 인식한다.
- 사용자 지정 템플릿 경로를 유지한다.
- 기존 내장 일간 계획·회고 템플릿은 `레거시 일간 계획 템플릿`으로 계속 선택 가능하게 둔다.

### 완료 조건

- [x] 모든 진입점이 같은 생성 함수와 템플릿 우선순위를 사용한다.
- [x] 같은 앱 창의 동시 두 번 실행은 날짜별 생성 Promise를 공유한다.
- [x] 생성된 페이지 ID에 템플릿을 적용하고 즉시 저장을 시도한다.

### P2 구현 결과 — 2026-08-22

- `src/lib/dailyNotes.ts`를 일간 노트 제목·탐색·템플릿·생성의 단일 진실 공급원으로 추가했다.
- 계획 허브, `Ctrl+Alt+D`, 월간 캘린더가 모두 `openOrCreateDailyNote()`를 호출한다.
- 저장 제목은 `일간 노트 YYYY-MM-DD`를 유지하며, 기존 `Daily Note YYYY-MM-DD`도 같은 날짜의 노트로 열고 목록·달력에 표시한다.
- 템플릿 우선순위는 모든 진입점에서 사용자 지정 → 내장 수정값 → 신규 기본값으로 통일했다.
- `addPage()`가 생성된 페이지 ID를 반환하게 하여, 생성 도중 다른 페이지가 선택돼도 잘못된 페이지에 템플릿을 적용하지 않는다.
- 같은 볼트와 날짜의 진행 중 생성 요청은 하나의 Promise를 공유한다. 서버의 제목 고유 제약은 없으므로 서로 다른 앱 창에서 동시에 만드는 경우까지 보장하지는 않는다.
- 기존 오프라인 폴백은 유지한다. 서버 저장 실패 시 로컬 초안을 자동 삭제하지 않으며, 기존 저장 상태·경고 흐름으로 사용자가 복구할 기회를 보존한다.
- 검증: TypeScript, 변경 파일 ESLint와 `git diff --check`를 통과했고, 세 진입점 외 직접 일간 생성 경로가 남지 않았음을 정적으로 확인했다.

## P3. 포스트잇 정리용 일간 템플릿

### 목표

포스트잇 한 장을 블록 하나로 빠르게 입력하고 처리할 수 있는 작업대를 제공한다.

### 기본 구조

```text
# YYYY-MM-DD

## 미처리 포스트잇
[한 장당 블록 하나]

## 오늘 기록으로만 남길 내용

## 처리 결과

## 마감 기록
```

### 작업

1. `포스트잇 야간 정리` 내장 템플릿 추가
2. 이 템플릿에는 Day Planner 블록을 넣지 않음
3. 템플릿을 일간 플래너 볼트의 일간 기본 템플릿으로 선택 가능하게 함
4. 템플릿을 켜도 오늘 일간 노트를 자동 생성하지 않음
5. 빈 블록을 과도하게 만들지 않고 첫 입력 위치에 자동 포커스
6. 일반 볼트에서는 이 템플릿을 기본값으로 강제하지 않음

### 완료 조건

- [x] 미처리 포스트잇의 빈 문단에서 Enter로 다음 블록을 연속 생성할 수 있다.
- [x] 입력 중 분류를 강제하지 않고 미처리 구역에 먼저 모은다.
- [x] 기존 사용자 지정 일간 템플릿이 계속 최우선으로 동작한다.

### P3 구현 결과 — 2026-08-22

- `포스트잇 야간 정리` 내장 템플릿을 추가했다. 구성은 날짜, 미처리 포스트잇, 오늘 기록, 처리 결과, 마감 기록이며 Day Planner는 포함하지 않는다.
- 각 구역에는 빈 문단 블록을 하나씩만 두고, 새 노트 생성 시 첫 `미처리 포스트잇` 블록으로 포커스와 스크롤을 이동한다.
- 볼트별 `planner.dailyNoteTemplate` 설정을 `standard` / `postit`으로 저장한다. 기본값은 `standard`다.
- 설정 → 볼트 기능에서 일간 플래너 볼트가 활성화된 경우에만 템플릿 선택 UI를 표시한다.
- 적용 우선순위는 사용자 지정 템플릿 → 현재 볼트의 포스트잇 템플릿 → 사용자가 수정한 표준 내장 템플릿 → 표준 기본값이다.
- 일반 볼트에서는 저장값이 있더라도 포스트잇 템플릿을 강제로 적용하지 않으며, 기존 노트도 변환하지 않는다.
- 검증: TypeScript, 변경 파일 ESLint, 볼트 설정 백엔드 테스트 2건과 `git diff --check`를 통과했다.
- 실제 다섯 장 연속 입력과 포커스의 체감은 사용자 볼트를 변경하지 않기 위해 자동 실행하지 않았으며, 아래 사용 관찰 관문에서 확인한다.

## P5. 빠른 블록 분류

### 목표

일간 노트의 포스트잇 블록을 적은 조작으로 처리한다.

### UI

```text
보내기
├─ 해야 할 일
├─ 장기 메모
└─ 아이디어
```

### 처리 계약

- 할 일: 목적지에 실제 `taskList` 블록을 생성한다.
- 장기 메모·아이디어: 목적지에 문단 블록을 생성한다.
- 일간 노트 원본은 그날의 역사로 남긴다.
- 원본에는 처리 종류·시각·목적지 상태만 표시한다.
- 이후 완료 상태는 `해야 할 일` 페이지의 실제 TaskList가 단일 진실 공급원이다.

### 중복 방지

1. 보내기 작업마다 고유 작업 ID 생성
2. 목적지 블록에 원본 페이지·블록 참조 저장
3. 목적지 저장 성공 후 원본을 처리 완료로 표시
4. 재시도 시 같은 원본 참조가 있으면 새 블록을 만들지 않음
5. 중간 저장 실패 시 복구 가능한 상태와 안내 제공

### 되돌리기

- 같은 페이지의 단순 상태 변경은 기존 undo에 포함한다.
- 페이지 간 전송은 두 페이지를 함께 복구할 수 있는 명시적 `보내기 취소`를 우선한다.
- 교차 페이지 작업을 일반 Ctrl+Z 하나에 암묵적으로 의존하지 않는다.

### 완료 조건

- 반복 클릭과 네트워크 재시도에도 목적지 블록이 하나만 생긴다.
- 목적지 저장 실패 시 원본이 처리 완료로 바뀌지 않는다.
- 기존 페이지 간 이동·복사 기능에 회귀가 없다.

## 7. 설정 데이터 초안

현재 볼트의 `_vault_preferences.json`을 확장하는 방향을 우선한다.

```json
{
  "planner": {
    "mode": "daily",
    "homePageId": "일정 홈 페이지 ID",
    "dailyWorkflow": {
      "templateMode": "postit",
      "taskPageId": null,
      "memoPageId": null,
      "ideaPageId": null
    }
  }
}
```

### 정규화 규칙

- 알 수 없는 `templateMode`는 안전한 기본값으로 복구한다.
- 빈 문자열 페이지 ID는 `null`로 정규화한다.
- 명시적인 `null` 업데이트로 연결을 해제할 수 있어야 한다.
- 예전 설정 파일에 `dailyWorkflow`가 없어도 일반 볼트는 `off`를 유지한다.
- 설정 파일 손상 시 사용자 페이지나 블록은 수정하지 않는다.
